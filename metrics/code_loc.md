# Implementation size

Code lines only (no comments or blank lines). Rust lines are classified by Verus' `line_count` (spec / proof / exec; `proof+exec` lines are counted with proof). Open Platform's ArduPilot VM glue is excluded from every total. Tests, runtime monitors, system-test and system-verification artifacts and generated tooling are reported separately in the last table. Each table is followed by a collapsible key that defines its columns in order.

<details>
<summary>Key</summary>

Columns, left to right:

- **Case study**: the system.
- **App exec (developer)**: Rust lines in Verus *exec* mode: executable code, i.e. function signatures and bodies, and data-type and constant declarations, that are not spec or proof, written or changed by the developer, in the thread crates (unit tests excluded). In practice this is the application code in the `*_app.rs` files.
- **App spec (developer)**: Rust lines in Verus *spec* mode: function contracts (`requires` / `ensures` / `recommends` / `decreases`, written either in `verus!` or as `#[verus_spec(...)]` attributes) and spec functions, written by the developer in the thread crates, e.g. spec helper functions or contracts on the developer's own helper functions. The contracts HAMR generates from GUMBO are not included here (next column).
- **App proof (developer)**: Rust lines in Verus *proof* mode: `proof { }` blocks, `assert` / `reveal` statements, loop `invariant` / `decreases` clauses and proof functions, plus lines that mix proof with exec code, written by the developer in the thread crates.
- **App contracts generated by HAMR**: lines HAMR writes into the thread crates' application files, inside its marker regions (`BEGIN MARKER` ... `END MARKER`): the Verus translation of each thread's GUMBO contract (requires / ensures, GUMBO functions, state-variable declarations) plus HAMR's preconditions from the AADL port semantics (e.g. output event ports empty at dispatch). All Verus modes together.
- **Developer libraries exec / spec / proof**: the same three counts (exec / spec / proof, developer-written) for library crates outside the thread crates: `firewall_core` and `mavlink_parser_vest/src/lib.rs` (Open Platform only).
- **Vest-generated parser exec / spec / proof**: exec / spec / proof lines of `mavlink_parser_vest/src/mavlink.rs`, which the Vest tool generates from the `mavlink.vest` format description (Open Platform only; the `.vest` file itself is not counted).

**Counting.** Only code lines are counted: blank and comment-only lines never are. Lines are classified with Verus' `line_count` tool (the source of the exec / spec / proof split); lines it does not classify (`use` imports, `type` aliases) are not counted.

</details>

<details>
<summary>Key</summary>

Columns, left to right:

- **Case study**: the system.
- **HAMR-generated**: lines of files HAMR regenerates on every run (header `Do not edit`: port APIs, data types, C wrappers, ...), plus lines of files without a HAMR header that are identical to HAMR's output (crate `lib.rs`, component C headers).
- **HAMR contract regions**: lines inside HAMR's marker regions (`BEGIN MARKER` ... `END MARKER`) of generate-once files: chiefly the Verus contracts translated from GUMBO.
- **HAMR template retained**: lines of generate-once files (header `will not be overwritten`, e.g. `*_app.rs`, `tests.rs`) that are still HAMR's template text, i.e. skeleton code the developer kept (found by matching the file against a fresh HAMR generation of the same model).
- **Developer**: lines written or changed by the developer: a line of a HAMR generate-once file that is not HAMR's template text, or a line of a file HAMR does not generate (e.g. `firewall_core`, the ethernet driver, the QEMU virtio client).
- **Vest-generated**: lines of `mavlink_parser_vest/src/mavlink.rs`, generated by Vest (Open Platform).
- **Total**: sum of the five provenance columns.
- **VM glue (excluded)**: lines of Open Platform's ArduPilot virtual-machine glue (C), shown for reference; not part of Total.

**What is included.** Rust and C code of the system: thread crates (without their unit tests), the GUMBO library crate, the data-type crate, developer library crates, the ethernet driver, and all C glue. Unit tests, monitoring, system testing and verification and scripts are in the last table.

**Counting.** Only code lines are counted: blank and comment-only lines never are. Lines are classified with Verus' `line_count` tool (the source of the exec / spec / proof split); lines it does not classify (`use` imports, `type` aliases) are not counted. A C line counts if it has any non-comment character.

</details>

<summary>Key</summary>

Columns, left to right:

- **Case study**: the system.
- **Role**: which part of the system's Rust code: *component* = the thread crates without their unit tests (application `*_app.rs` files and HAMR's generated port APIs, `lib.rs`, logging); *developer-library* = `firewall_core` and `mavlink_parser_vest`; *driver* = Open Platform's ZCU102 ethernet driver (`crates/*/core`, not verified); *gumbo-library* = the crate HAMR generates from the GUMBO library package (`GumboLib` / `GUMBO_Library`); *data* = the crate HAMR generates for the model's data types.
- **exec**: Rust lines in Verus *exec* mode: executable code, i.e. function signatures and bodies, and data-type and constant declarations, that are not spec or proof.
- **spec**: Rust lines in Verus *spec* mode: function contracts (`requires` / `ensures` / `recommends` / `decreases`, written either in `verus!` or as `#[verus_spec(...)]` attributes) and spec functions.
- **proof**: Rust lines in Verus *proof* mode: `proof { }` blocks, `assert` / `reveal` statements, loop `invariant` / `decreases` clauses and proof functions, plus lines that mix proof with exec code.
- **trusted**: Rust lines of code Verus assumes rather than checks: items marked `#[verifier::external_body]` (e.g. logging and C-interface wrappers), `assume` / `admit` and `assume_specification`.
- **other**: remaining Rust lines: attributes such as `#[cfg(...)]`, `#[derive(...)]` or `#[verifier::...]` (other than doc comments and `#[verus_spec]`), `mod x;` declarations and `macro_rules!` definitions.
- **total**: sum of exec, spec, proof, trusted and other.

All provenances (generated and developer-written) together; C is not included.

**Counting.** Only code lines are counted: blank and comment-only lines never are. Lines are classified with Verus' `line_count` tool (the source of the exec / spec / proof split); lines it does not classify (`use` imports, `type` aliases) are not counted.

</details>

<details>
<summary>Key</summary>

Columns, left to right:

- **Case study**: the system.
- **Requirements**: lines of the case study's requirements documents (`requirements/*.md`): every non-blank line. Requirements kept as PDF are listed by page count, since a PDF has no countable source lines.
- **Makefiles**: lines of `Makefile`s and `*.mk` files: non-blank lines that are not `#` comments.
- **TOML**: lines of Cargo manifests and Rust toolchain files (`Cargo.toml`, `rust-toolchain.toml`): non-blank lines that are not `#` comments.
- **Build and deploy scripts**: lines of build and deployment scripts: the Microkit system-description scripts (`meta.py`, `sdfgen_helper.py`), shell scripts, Docker files (`Dockerfile`, `*.yml`) and the HAMR codegen scripts (`sysml/bin/*.cmd`); non-blank lines that are not comments.
- **Documentation**: lines of Markdown documents (`*.md`) other than requirements, e.g. readmes and HAMR's generated notes: every non-blank line. The case study's own `readme.md` in this repository is not counted.
- **Vest format specification**: lines of `.vest` files (`mavlink.vest`, from which Vest generates the MAVLink parser): non-blank lines that are not comments.
- **Total**: sum of the line columns (PDF pages not included).

Each cell is *lines (of which developer-written)*. Lines in HAMR's output directory are attributed as in the tables above (a Makefile or Cargo manifest is HAMR-generated unless the developer changed it); files outside it (requirements, `sysml/bin` scripts, upstream readmes) count as developer-written. Files of the separately reported artifacts (test scheduler, monitors, `bin/`) and of the VM glue are not included; these line-counting rules follow the PROVERS effort measurer (spec M-9, M-10).

</details>

- **Other files**: lines of its other text files (Slang `.cmd` scripts, `.mk` / `.meta.py` build configurations): non-blank lines, without `//` and `/* */` comments in `.cmd` scripts or `#` comments in make / Python / shell / TOML files.

**Counting.** Only code lines are counted: blank and comment-only lines never are. A C line counts if it has any non-comment character.

</details>
